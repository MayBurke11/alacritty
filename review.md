# Архитектурное ревью форка: `stable-pre-tiling` → `tab-dev` HEAD

Диапазон: `stable-pre-tiling..tab-dev` (92 коммита, +9320/−512 строк).
HEAD: `29417423 docs: feature ideas`.
Сборка: `cargo build --bin alacritty` — **успешно**, 4 предупреждения (все подтверждают
находки о мёртвом коде ниже).

Общая оценка: форк добавил большой пласт функциональности (tabs, IPC, modal menu,
tiling, session save/restore) поверх однотерминальной модели Alacritty. Функционально
многое работает, но архитектура получилась «наращенной сбоку»: `WindowContext` и
`Display::draw` превратились в god-объекты, есть один случай **нарушения памяти-safety
(UB)**, несколько **функциональных багов** в дереве панелей и IPC, и системные проблемы
совместимости с терминальными приложениями из-за жёстко зашитого перехвата клавиш.

Ниже — значимые проблемы по областям, отсортированные по критичности внутри области, с
путями решения.

---

## 0. Критично / сквозные проблемы

### 0.1. UB: приведение `&Notifier` к `*mut Notifier` (unsound)
`alacritty/src/window_context.rs:1701-1715`

```rust
} else if let Some(pane) = tab.additional_panes.get(&active_pid) {
    let lock = pane.terminal.lock();
    let np = &pane.notifier as *const Notifier as *mut Notifier; // <- immutable → mutable
    (lock, np, pane.master_fd, pane.shell_pid)
}
...
let notifier = unsafe { &mut *notifier_ptr };
```

Здесь из **разделяемой ссылки** (`tab.additional_panes.get(...)` заимствует неизменяемо)
создаётся `&mut Notifier`. Это undefined behavior в Rust (нарушение aliasing-правил),
даже если на практике «работает». Обход сделан только чтобы победить borrow-checker при
сборке `ActionContext { notifier: &mut Notifier, ... }`.

**Решение (по возрастанию усилий):**
1. `Notifier::send` требует лишь `&self` (внутри `mpsc::Sender`). Изменить сигнатуру
   `ActionContext.notifier` на `&Notifier` (или на тонкий трейт `Notify`), убрав
   `&mut` полностью — тогда raw-pointer каст не нужен.
2. Либо получить `&mut` через `get_mut` (нужен `&mut tab.additional_panes`) и переверстать
   заимствования: сначала снять неизменяемые данные (`master_fd`, `shell_pid`) в локальные
   переменные, затем брать `get_mut`.
3. Идеально — вынести «активный терминал + notifier» в отдельную абстракцию
   `ActivePane<'a>`, единый источник для `handle_event`/`draw`.

### 0.2. `#![allow(dead_code)]` маскирует незавершённые фичи
`pane_tree.rs:1`, `pane_state.rs:1`.

Файлы целиком глушат предупреждения о мёртвом коде. Компилятор всё же нашёл в
`window_context.rs`: `divider_drag` (никогда не читается), методы `active_terminal`,
`active_terminal_for`, `pane_at_position`, `divider_at_position` — **не вызываются**.
Значит **мышиный фокус панели и перетаскивание разделителя не подключены** — фичи
заглушены, но не работают (см. 3.4). `allow(dead_code)` не даёт это заметить.

**Решение:** убрать глобальный `allow(dead_code)`; либо доделать mouse-роутинг панелей,
либо удалить стабы. Для реально нужного будущего API помечать точечно
`#[allow(dead_code)]` над конкретным элементом с комментарием-обоснованием.

### 0.3. God-объекты `WindowContext` и `Display::draw`
`WindowContext` вырос до ~2300 строк и совмещает: управление вкладками, панелями,
меню, редакторы заголовка/команды, session save/restore, диалог закрытия окна, IPC-хендлеры.
`Display::draw` получил 11 позиционных аргументов (`pane_clip`, `is_active_pane`,
`skip_present`, `menu_state`, ...) и три почти дублирующих ветки рендера
(`window_context.rs:1398-1526`).

**Решение:** выделить модули/типы: `TabManager`, `PaneManager` (владеет `pane_tree` +
`additional_panes` + resize-логикой), `MenuController`, `SessionStore`. Заменить длинный
список аргументов `draw` на структуру `DrawParams { clip, active, present, menu, ... }`.
Это резко снизит связность и облегчит тестирование.

## 1. Tabs + IPC (create/list/close/pin/save)

### 1.1. IPC-команды игнорируют `window_id` и бьют по «первому» окну (недетерминированно)
`event.rs:432-468`

`SelectTab`, `CloseTab`, `PinTab`, `QuickRun` делают:
```rust
for window_context in self.windows.values_mut() { window_context.select_tab_at(...); break; }
```
`self.windows` — `HashMap`, порядок итерации **не определён**. При нескольких окнах
команда попадёт в случайное окно. `ListTabs`/`SaveTabs` аналогично берут
`.values().next()`. Только `CreateTabIPC` корректно фильтрует по `window_id`
(`event.rs:410-419`). В `ipc.rs:96-114` `window_id` для этих сообщений вообще не читается.

**Решение:** протянуть `window_id` (как в `CreateTab`) во все tab-сообщения
`SocketMessage` и фильтровать окна одинаково. При отсутствии `window_id` — определить
явную политику (например, окно с фокусом), а не полагаться на порядок `HashMap`.

### 1.2. `--restore` применяется ко всем окнам сразу
`event.rs:248-259` — цикл `for wc in self.windows.values_mut() { wc.restore_tabs(...) }`.
Обычно окно одно, но при `--daemon`/нескольких окнах сессия «размножится».

**Решение:** восстанавливать только в только что созданное initial-окно.

### 1.3. Гонка/дублирование при закрытии вкладки
`close_tab_at`/`close_active_tab` вызывают `terminal.lock().exit()`, а фактическое
удаление вкладки происходит асинхронно в `handle_pane_exit`→`handle_tab_exit` по событию
`Exit`. Индекс, переданный по IPC, к моменту обработки может «съехать» (другой tab закрылся).
Пиннинг проверяется в момент запроса, но не в момент удаления.

**Решение:** оперировать `TabId`, а не индексом, во всех отложенных операциях; проверять
инварианты (pinned, существование) на стадии применения.

### 1.4. Заголовок вкладки: fork-специфичная эвристика процессов Linux-only
`window_context.rs:56-105` (`foreground_process_name`, `tcgetpgrp`, `/proc/<pid>/comm`,
`is_shell_process`). Работает только на Linux (`/proc`), гистерезис (два совпадения)
`refresh_detected_title` — рабочий, но это самодельный аналог того, что делают osc-title.

**Решение:** это приемлемо как эвристика, но стоит документировать Linux-only и
предусмотреть fallback на macOS/BSD (там нет `/proc`).

## 2. Modal menu bar (Ctrl+G, буквенная навигация, list mode, вложенные подменю)

Логика состояния (`event.rs:MenuState`, 760-963) сама по себе аккуратная: `path` как стек
индексов в дерево, `list_mode`, `select/back/items_at`. Это лучшая по чистоте часть форка.
Проблемы — в интеграции.

### 2.1. Дублирование обработчиков меню: `TabAction::*` и `MenuOp::*`
`window_context.rs:1608-1670` (в `TabAction`) и `1773-1829` (в `menu_op_pending`) содержат
**идентичные** реализации `FocusLeft/FocusRight/Select/Back/Click/LetterKey`, включая
копипаст цикла подбора буквы (`1655-1668` ≈ `1806-1821`). Плюс дубли в
`handle_menu_selection`. Есть «двойной путь»: асинхронный (события) и синхронный
(`menu_op_pending`), причём `TabAction::MenuCommand` помечен «Legacy — handled by MenuClick».

**Решение:** оставить **один** путь (синхронный `menu_op_pending`, ради «no frame delay»),
удалить дублирующие `TabAction::Menu*`. Вынести подбор буквы в
`MenuState::select_by_letter(&menu, ch)`.

### 2.2. Отладочные `log::debug!` пересчитывают `bar_labels` в hot-path
`window_context.rs:1765-1768, 1774-1776, 1825-1828` — на каждую menu-операцию собирается
`bar_labels(...)` (обход конфига + дерева панелей + аллокации). `log!` ленив на выводе, но
захват аргументов пишется в биту макроса; в целом шумно и легко забыть, что это исполняется.

**Решение:** убрать/свернуть отладочные логи, либо обернуть в `if log_enabled!(Debug)`.

### 2.3. `action` — «stringly-typed»
`config/menu.rs:29` `action: Option<String>`; диспетчеризация — `match action.as_str()` с
`_ => {}` (`window_context.rs:708-772`). Опечатка в конфиге тихо ничего не делает.

**Решение:** сделать `enum MenuAction` с `#[serde(rename_all="kebab-case")]`; неизвестное
значение → ошибка парсинга конфига с сообщением в message bar.

### 2.4. Сессии/FS-логика зашита в `MenuState::select`
`event.rs:878-905` — прямое чтение `~/.config/alacritty/sessions/` внутри состояния меню.
Смешение UI-состояния и файловой системы усложняет тесты.

**Решение:** вынести провайдер списков (`ListProvider`) наружу; `MenuState` должен только
хранить уже полученные элементы.

## 3. Tiling / panes (бинарное дерево, split, focus, resize, zoom, close)

### 3.1. БАГ: `find_split_by_divider_index` использует неверный порядок обхода
`pane_tree.rs:246-262`

```rust
fn find_split_index_impl(&self, target, index) -> Option<SplitId> {
    if let Split { split_id, a, b, .. } = self {
        a.find_split_index_impl(target, index);   // <- результат ОТБРАСЫВАЕТСЯ
        if *index == target { return Some(*split_id); }
        *index += 1;
        b.find_split_index_impl(target, index)
    } else { None }
}
```
Две ошибки:
1. Возврат из рекурсии в `a` **игнорируется** — совпадение внутри левого поддерева никогда
   не возвращается.
2. Порядок нумерации здесь **in-order** (`a`, self, `b`), а `compute_rects`
   (`pane_tree.rs:284-297`) складывает разделители **pre-order** (divider сначала, потом
   `a`, потом `b`). Индексы не совпадают на вложенных раскладках.

Итог: `divider_at_position` (`window_context.rs:2058-2071`) вернёт неверный `SplitId` при
3+ панелях. Функция сейчас не вызывается (см. 0.2), но при подключении mouse-drag это
приведёт к перетаскиванию «не того» разделителя. Юнит-теста на неё нет.

**Решение:** переписать через единый pre-order обход, согласованный с `compute_rects`,
возвращая результат рекурсии:
```rust
fn find(&self, target, idx) -> Option<SplitId> {
    if let Split{split_id,a,b,..} = self {
        if *idx == target { return Some(*split_id); }
        *idx += 1;
        a.find(target, idx).or_else(|| b.find(target, idx))
    } else { None }
}
```
Добавить тест на 3–4 панели.

### 3.2. Коллизия `SplitId`/`PaneId` после restore
`window_context.rs:2089-2091` — `next_pane_id` инкрементируется и для `PaneId`, и для
`SplitId` из одного счётчика (ок). Но при restore (`934-935`) `next_pane_id` берётся как
`max(pane_id) + 1`, **игнорируя `SplitId` в восстановленном дереве**. Новый split после
restore может получить `SplitId`, уже присутствующий в дереве → неоднозначность при resize
по split-id.

**Решение:** хранить единый монотонный счётчик и на restore восстанавливать его как
`max(все pane_id ∪ все split_id) + 1`; либо сериализовать сам `next_pane_id`.

### 3.3. Пиксель→ячейка: рассинхрон scissor-клипа и смещения ячеек
`display/mod.rs:876-897` — смещение ячеек панели считается округлением
`(px / cell_w).round()`, а `split_rect` (`pane_tree.rs:311-334`) режет ширины через
`floor` в пикселях, а сам scissor — в пикселях. Округление vs floor даёт разъезд на 1
столбец/строку на некоторых размерах окна. Это же — корень OOB в damage-трекере, который
«залечен» заглушками:

`display/damage.rs` (новый код):
```rust
pub fn damage_line(&mut self, damage) {
    if damage.line >= self.lines.len() { self.full = true; return; } // маскировка
    ...
}
pub fn damage_point(&mut self, point) {
    if point.line >= self.lines.len() { return; } // молча теряем
}
```
Панели рендерятся через **один** `Display`, размер damage-трекера = строкам полного окна, а
терминал панели меньшего размера смещается и вылезает за границы.

**Решение:** сделать координаты панели производными от **целых ячеек** (а не пикселей):
считать split в единицах колонок/строк, из них выводить и пиксельный rect, и cell-offset —
тогда клип и смещение согласованы by construction, а OOB-заглушки не нужны. Долгосрочно —
вынести damage-трекинг на уровень панели (per-pane `FrameDamage`), а не полного окна;
сейчас multi-pane фактически всегда рисует «full damage», теряя оптимизацию partial-damage.

### 3.4. Мышь для панелей не подключена (мёртвый код)
`pane_at_position`, `divider_at_position`, `divider_drag` — определены, но не используются
(подтверждено предупреждениями сборки). Клик по неактивной панели её не фокусирует;
разделитель нельзя тянуть мышью.

**Решение:** либо подключить в `input/mod.rs` (в `on_mouse_press`, рядом с уже
подключёнными `menu_at_mouse`/`tab_at_mouse`), либо удалить до реализации.

### 3.5. `PaneId(0)` как sentinel и как реальный id
`pane_tree.rs:67,128,137` — `PaneId(0)` одновременно «дефолт/заглушка при опустошении» и
**реальный** id первой панели (`window_context.rs:203`). Ветвления `if pane_id == PaneId(0)`
разбросаны по всему коду (draw, resize, handle_event). Это хрупко: логика «pane 0 живёт в
`tab.terminal`, остальные в `additional_panes`» — раздвоение хранилища.

**Решение:** унифицировать — либо все панели в `HashMap<PaneId, PaneState>` (включая
первую), либо ввести `Option<PaneId>`/`NonZero` для sentinel. Убрать спец-кейс «panel 0».

### 3.6. Клоны всего дерева в `remove`
`pane_tree.rs:105-146` — `CollapseToSibling(self.clone())` клонирует поддерево на каждом
уровне подъёма. Для больших раскладок это O(n²). Приемлемо для нескольких панелей, но
стоит переписать на in-place мутацию (`std::mem::replace` дочернего узла) без клонов.

### 3.7. Повторные `leaf_ids()` за кадр
В `draw` и хендлерах `leaf_ids()` (аллоцирует `Vec` + рекурсия) вызывается многократно
(`window_context.rs:1420,1494,1656,...`). Мелочь, но легко закешировать `pane_count`.

## 4. Session save/restore (`pane_tree` + команды)

### 4.1. Реинъекция команд в шелл — ненадёжно и небезопасно
`window_context.rs:1833-1863` — восстановление «команд» панели делается записью строки в
PTY (`Msg::Input(cmd + "\n")`), то есть **выполнением произвольной строки в шелле**.
Источник команды — `foreground_process_cmdline` (`/proc/<pid>/cmdline`, `856-862`).
Проблемы:
- Комментарий говорит «wait 1s for shell init», а код инъектирует немедленно (противоречие).
- cmdline процесса ≠ команда, которую можно повторно ввести в шелл (интерактивные TUI,
  пути, аргументы с пробелами, шелл сам как `-zsh`).
- Автовыполнение восстановленной строки — потенциальный риск (сессия из недоверенного
  файла выполнит команды).

**Решение:** не «переигрывать» команды вводом в шелл. Варианты: (а) восстанавливать только
рабочую директорию (`cwd`) и раскладку, оставляя панели с чистым шеллом; (б) если нужно
перезапускать процесс — стартовать PTY прямо с этой командой (`terminal_options.command`),
а не печатать в существующий шелл; (в) явное подтверждение перед авто-run.

### 4.2. Порядок восстановления вкладок держится на неявных инвариантах
`restore_tabs` (`877-979`): для `i==0` удаляет `tabs[0]` и создаёт, для прочих создаёт;
далее адресует `self.tabs[i]`, полагаясь, что созданная вкладка встала ровно в индекс `i`.
Также `wd.map(|p| p)` (`914,918`) — no-op identity map (мёртвый код).

**Решение:** сохранять `TabId` создаваемых вкладок и адресовать по id; убрать `.map(|p| p)`.

### 4.3. Save использует прямой доступ к `/proc`, дублируя логику
`tabs_save_json` (`853-871`) читает `/proc/<pid>/cwd` инлайн, при этом рядом уже есть
`process_cwd`. Дублирование.

**Решение:** переиспользовать `process_cwd`; вынести (де)сериализацию сессии в отдельный
модуль `session.rs` с версионированием схемы (сейчас схема без версии — миграции сломаются).

## 5. Перехват клавиш (`input/keyboard.rs`) — совместимость с терминалом

### 5.1. Ctrl+G жёстко перехвачен глобально (ломает BEL и TUI)
`keyboard.rs:137-144` — Ctrl+G всегда переключает меню, **до** системы биндингов и до
записи в PTY. В терминале Ctrl+G — это `^G` (BEL) и активно используется в bash/readline
(`abort`), Emacs, многих TUI. Теперь эта комбинация недоступна приложениям **без
возможности отключить**.

**Решение:** сделать переключатель меню обычным `Action` в биндингах (по умолчанию можно
оставить Ctrl+G, но через конфиг), чтобы пользователь мог переназначить/убрать. Не хардкодить
в `key_input` раньше `process_key_bindings`.

### 5.2. Alt+стрелки перехвачены по умолчанию (ломает навигацию по словам)
`config/bindings.rs` (диф) — дефолтные биндинги `Alt+Arrow → FocusLeft/Right/Up/Down`.
Alt+←/→ широко используется как «переход по словам» в readline/редакторах. Плюс
`resize` mode (`keyboard.rs:110-134`) перехватывает Alt+стрелки жёстко.

**Решение:** не включать Alt+arrow пановые биндинги по умолчанию (в комментарии уже написано
«optional» — так и сделать: закомментировать в дефолтах, оставить только через modal menu).
Перехваты в `key_input` для resize-режима допустимы, т.к. режим явно активирован
пользователем, но должны иметь чёткий Escape-выход (он есть).

### 5.3. Модальный режим меню молча глотает все клавиши
`keyboard.rs:165-175` — `// All other keys are suppressed ... return;`. Это by design
(Zellij-подобно), но нет обратной связи, если пользователь не осознал, что он в modal-режиме.

**Решение:** индикатор в баре уже есть (`ACTIVE`/`LOCKED`) — ок; стоит добавить, что
неизвестная буква ничего не делает (визуальный «мигок» или ничего) — минорно.

## 6. Рендеринг меню/панелей (`display/mod.rs`)

### 6.1. Три ветки рендера с копипастом выбора терминала
`window_context.rs:1399-1526` — zoomed / multi-pane / single, каждая заново реализует
`if pane==0 {tab.terminal} else if additional_panes.get {...} else {...}`. Тот же шаблон
повторяется в `handle_event`, `split_pane`, `toggle_zoom`, `resize_pane`, `close_pane`,
`handle_pane_exit` — 8+ раз. Уже есть `active_terminal_for`, но он **не используется**
(мёртвый код, 0.2).

**Решение:** ввести `PaneManager::terminal(pane_id) -> Arc<FairMutex<...>>` и
`PaneManager::for_each_leaf(...)`; заменить все копии.

### 6.2. Ручное управление `gl::Scissor`/`SCISSOR_TEST` вне рендерера
`display/mod.rs:863-874,1044`, `window_context.rs:1455`. Прямые unsafe GL-вызовы из
window_context (`unsafe { gl::Disable(SCISSOR_TEST) }`) размывают границу «рендерер владеет
GL-состоянием». Легко оставить scissor включённым и получить артефакты (уже есть ручные
`Disable` в нескольких местах как компенсация).

**Решение:** инкапсулировать scissor в `Display`/`Renderer` (RAII-guard `ScissorClip`,
который включает в конструкторе и выключает в `Drop`).

### 6.3. Захардкоженный цвет разделителя
`window_context.rs:1428` — цвет divider `Rgb{196,154,247}` зашит в код.

**Решение:** вынести в конфиг (`panes.divider_color` / `panes.divider_width`).

## 7. Методология pixel-testing (`docs/pixel-testing.md`) и E2E

### 7.1. Не автоматизировано и хрупко
Метод завязан на X11 (`xdotool`, `import`, `--class Alacritty`), не работает на Wayland;
использует `sleep`-тайминги (гонки), захардкоженные пиксельные координаты и цвета конкретной
темы (`focus_nova`). Нет golden-image сравнения с допуском, нет запуска в CI.
E2E-скрипты (`scripts/e2e-*.sh`) — bash, вне `cargo test`, требуют реального дисплея и
`alacritty msg`.

**Решение:**
- Оставить документ как «dev-методику», но явно пометить X11-only и нестабильность таймингов
  (заменить `sleep` на ожидание готовности окна).
- Для регрессий рендера — headless golden-тесты через существующий `ref_test`
  (`write_ref_test_results`, `window_context.rs:1948`), сравнивая grid.json, а не пиксели.
- Логику раскладки (`pane_tree`, `split_rect`, `bar_labels`, `MenuState`) покрыть **юнит-**
  тестами (чистые функции, дисплей не нужен) — это устранит зависимость от скриншотов для
  большинства багов из 3.x/2.x. Сейчас нет тестов на `find_split_by_divider_index`,
  `focus_pane`, `adjust_ratio` со знаком, `bar_labels`.

### 7.2. E2E не интегрированы в CI
`.github/workflows/ci.yml` — Linux-only, без clippy (отключён). Скрипты E2E не вызываются.

**Решение:** вернуть `clippy -D warnings` хотя бы на новый код (нашёл бы UB-каст и dead-code);
добавить `cargo test` (юнит) в CI; E2E оставить ручными или запускать в Xvfb отдельным
джобом.

## 9. Вердикт: жизнеспособность

**Короткий ответ: жить будет.** Форк собирается и функционирует, фундамент вменяемый
(бинарное дерево панелей, modal-menu state machine, IPC поверх штатного) и расширяемый.
Ни одна из находок не является фатальной архитектурной ошибкой, требующей переписать всё
с нуля — этого делать не нужно.

**Три вещи, которые нельзя оставлять как есть:**
1. **UB с `*const → *mut Notifier` (0.1)** — формально unsound. Сейчас «работает», но это
   мина: апгрейд компилятора или рефакторинг рядом может дать реальный сбой. Единственный
   пункт, обязательный к правке. Чинится за ~полчаса.
2. **Хардкод Ctrl+G и Alt+стрелок (5.1, 5.2)** — не баг кода, а продуктовое решение,
   которое тихо ломает bash/readline/emacs/vim/tmux у любого пользователя, без возможности
   отключить. Это то, за что прилетят баг-репорты в первый же день. Дёшево исправить.
3. **Реинъекция команд в шелл при restore (4.1)** — работает в демо, разваливается на
   реальных кейсах (TUI, пробелы, пути) + риск авто-выполнения. Не влияет на стабильность,
   но фича по сути ненадёжная.

**Остальное** (god-объекты, дубли путей меню, мёртвый код мыши, рассинхрон пиксель/ячейка,
тесты) — это долг сопровождаемости. Он не мешает «жить», но каждая новая фича будет даваться
дороже, а OOB-заглушки в damage-трекере намекают, что багов рендера дальше будет больше.

**Практический итог:**
- **Для личного использования / раннего релиза** — уже сейчас пригодно, если закрыть п.1 и
  п.2 (обязательный минимум) из первого спринта.
- **Для проекта с внешними пользователями** — сначала весь первый спринт (раздел 8, 6 пунктов),
  затем постепенный рефакторинг god-объектов и перевод раскладки на cell-based координаты.

Переписывать с нуля смысла нет — дешевле итеративно вычистить перечисленный долг.

## 10. Дополнения после сверки с `review.md` и `review2.md`

Ниже — значимые находки из двух других ревью, которые не были покрыты выше. Мелкие
стилистические замечания (брейс-стиль, комментарии-разделители) опущены как незначимые.

### 10.1. `tabs_save_json` не имеет `#[cfg]` — не соберётся на Windows (портируемость)
`window_context.rs:854` — `std::fs::read_link(format!("/proc/{}/cwd", tab.shell_pid))`.
Поле `tab.shell_pid` объявлено под `#[cfg(not(windows))]` (`window_context.rs:134-135`), а
сама `tabs_save_json` — нет. Соседние `foreground_process_*` корректно закрыты `#[cfg]`, а
эта функция обращается к `shell_pid`/`master_fd` напрямую → **на Windows код не
скомпилируется**. CI сейчас Linux-only (проблема замаскирована), но это блокер для
кроссплатформенности.

**Решение:** закрыть `/proc`-доступ и обращения к `shell_pid`/`master_fd` под
`#[cfg(not(windows))]`, вынести кросс-платформенный запрос cwd в `platform`-модуль
(перекликается с 1.4).

### 10.2. `focus_pane`: fallback «оборачивается» на несвязную панель (UX)
`window_context.rs:2201` — если в запрошенном направлении панели нет, фокус прыгает на
«следующую» панель по порядку листьев:
```rust
let new_active = if let Some((id, _)) = best { id }
    else { leaves[(pos(active) + 1) % leaves.len()] };
```
Пользователь нажал «фокус влево», а фокус ушёл на произвольную панель.

**Решение:** при отсутствии кандидата в направлении — **ничего не делать** (как в tmux/Zellij
по умолчанию), либо сделать «wrap» опцией конфига.

### 10.3. `resize_pane`: шаг ресайза захардкожен 5%
`window_context.rs:2248` — `let delta = 0.05;`. Не зависит от размера окна/числа панелей: на
маленьком окне грубо, на большом — мелко.

**Решение:** вынести шаг в конфиг (`panes.resize_step`); опционально масштабировать от
размера окна в ячейках.

### 10.4. `mark_fully_damaged` вызывается повсеместно — сводит на нет damage-трекер (perf)
`mark_fully_damaged()` (пара `frame()` + `next_frame()`) встречается ~20 раз: почти каждая
операция с вкладками/панелями (`set_active_tab`, `create_tab_inner`, `move_active_tab`,
`split_pane`, `close_pane`, `toggle_zoom`, `resize_pane`, `handle_pane_exit`, restore, ...)
запрашивает полную перерисовку. Это шире, чем частный multi-pane OOB из 3.3: даже переключение
вкладки перерисовывает весь кадр. Для эмулятора терминала инкрементальный damage — ключ к
производительности.

**Решение:** ввести хелперы `mark_pane_damaged(pane_id)` / `mark_all_damaged()` (объединив
разбросанные `dirty` + `pending_update.dirty` + damage-вызовы), и повреждать только затронутые
прямоугольники панелей, которые и так уже вычисляются. Переключение вкладки объективно требует
full damage, а вот resize/focus одной панели — нет.

### 10.5. Непоследовательная маршрутизация menu-действий (proxy-событие vs прямой вызов)
`window_context.rs:708-772` — часть действий шлётся через `event_proxy.send_event(...)`
(`create-tab`, `close-tab`, `rename-tab`, `move-tab-*`), часть вызывается напрямую
(`pin-tab` → `self.toggle_pin_at`, `split-*`/`close-pane`/`focus-*` → методы). Разные пути
дают разную задержку в кадрах и усложняют трассировку.

**Решение:** унифицировать — либо все действия через один синхронный диспетчер
(перекликается с 2.1, где предложено оставить единый `menu_op_pending`-путь).

### 10.6. `close_pane` и `handle_pane_exit` — почти дублирующая логика
`window_context.rs:2135-2169` и `2265-2307` реализуют один и тот же паттерн «найти соседа →
удалить из дерева → ресайзнуть оставшуюся». Разница лишь в том, что `handle_pane_exit`
проваливается в `handle_tab_exit`, когда закрылась последняя панель.

**Решение:** выделить общий `remove_pane(tab_idx, pane_id) -> RemainingPanes` и вызывать из
обоих мест.

### 10.7. Letter-key: `to_lowercase()` аллоцирует (мелкая perf)
`window_context.rs:1657, 1808` и `event.rs` — подбор буквы использует `to_lowercase()`
(даёт `String` для мультисимвольных случаев). Для меню достаточно `to_ascii_lowercase()` без
аллокации.

**Решение:** заменить на `eq_ignore_ascii_case`/`to_ascii_lowercase` при сравнении первых
букв меток.

### 10.8. Scissor выключается без восстановления предыдущего состояния
Уточнение к 6.2: `window_context.rs:1455` и `display/mod.rs:1044` делают
`gl::Disable(SCISSOR_TEST)`, не сохраняя/не восстанавливая прежнее состояние. Пока работает
за счёт того, что клип каждый раз ставится заново, но это хрупко.

**Решение:** RAII-guard `ScissorClip` (см. 6.2), который снимает клип в `Drop`, вместо ручных
`Disable`.

## 11. Что проверено и работает корректно

Не всё в диффе проблемно — ниже то, что я (и перекрёстно review2.md) проверил и счёл
сделанным правильно. Полезно как ориентир, что **не** нужно трогать при рефакторинге.

- **Общая декомпозиция подсистем.** Каждая вкладка владеет своим `PaneNode`-деревом; каждый
  терминал получает `EventProxy`, помеченный `(window_id, tab_id, pane_id)`; события
  маршрутизируются по этим меткам верно (`event.rs`). Три подсистемы (tabs/menu/panes)
  наслоены чисто.
- **`PaneNode` (ядро дерева)** — аккуратный дизайн: `split`/`remove`/`leaf_rects` логически
  верны, `adjust_ratio` через `SearchResult(Found/Adjusted/NotFound)` корректно предотвращает
  двойную корректировку ratio; клампы `[0.1, 0.9]` единообразны. 15 юнит-тестов покрывают
  основные случаи. (Исключение — `find_split_by_divider_index`, см. 3.1.)
- **`MenuState` (state machine меню)** — чистая: `path` как стек индексов в дерево,
  `select/back/items_at/item_count`, `list_mode`. `bar_labels` корректно показывает пункты
  только при `active=true`, `labels[0]` — индикатор режима, `focus` начинается с 1 —
  индексация согласована (фикс `4d743ad0`).
- **Синхронный путь меню (zero-frame latency).** `Ctrl+G`→`menu_toggle_pending`,
  `Alt+стрелки/Enter/Escape/буквы/клик`→`menu_op_pending`, применяются синхронно после цикла
  событий. Дизайн правильный (претензия только к дублированию с `TabAction`, см. 2.1).
- **Приоритет перехвата клавиш** (`keyboard.rs`): close-confirmation → редакторы
  title/run → resize-режим → Ctrl+G → активное меню → обычные биндинги. Порядок верный,
  каждый guard делает ранний `return`, клавиши не «протекают». (Отдельно от вопроса, что
  Ctrl+G/Alt-стрелки не отключаемы — см. 5.1/5.2.)
- **Z-order многопанельного рендера**: контент панелей → разделители → tab bar → menu bar →
  футеры редакторов → `present()`. Порядок корректный.
- **Курсор только на активной панели** (`display/mod.rs`): rects курсора обрезаются для
  неактивных панелей, у активной — транслируются на `(col_offset, line_offset)`. Верно.
- **`mouse_point` клампится** к `last_column()`/`bottommost_line()` — предотвращает OOB, когда
  мышь в scissored-панели, а грид меньше прямоугольника панели.
- **Slant/AA рендер таб-сепаратора** (`add_slanted_separator_rects` + `add_antialiased_strip`)
  — корректная субпиксельная антиалиасинг-реализация без кастомного шейдера.
- **`handle_tab_exit`: стабильность индекса.** После `tabs.remove(index)` пересчёт
  `active_tab` через `saturating_sub(index < active_tab)` верен; поиск следующей активной по
  `tab_id` устойчив к сдвигу индексов.
- **`ActionContext`-трейт** с ~50 методами-дефолтами (`{}`) — идиоматичный Rust для
  опциональной функциональности; `#[cfg(not(target_os="macos"))]` на tab-действиях корректно
  избегает конфликта с нативными вкладками macOS.
- **Гистерезис заголовка вкладки** (`refresh_detected_title`, «два совпадения подряд») —
  рабочий способ отфильтровать транзиентные процессы (`ls`, `cat`) из заголовка.

> Примечание: в review2.md реинъекция команд при restore и OOB-guards damage названы
> «корректными/good». Я с этим **не** согласен: OOB-guards — это маскировка причины (см. 3.3),
> а реинъекция ненадёжна (см. 4.1). Поэтому в список «работает корректно» они не внесены.
